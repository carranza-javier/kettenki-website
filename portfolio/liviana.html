Liviana

Öffentlicher KI-Chatbot auf kettenki.com, zugleich Produkt und eigene Demo

Kontext

Liviana ist eines der drei Produkte von KettenKI: ein Chatbot, der Kundenanfragen auf der Website eines Unternehmens beantwortet. Sie auf kettenki.com selbst laufen zu lassen, macht sie zu beidem gleichzeitig. Wer hier fragt, was Bambera kann, benutzt in diesem Moment Liviana und sieht sie arbeiten. Das unterscheidet sie von jedem anderen Stück in diesem Portfolio: Es ist kein Screenshot und kein Repository, es ist ein Produkt, das die Besucherin im selben Besuch ausprobieren kann. Technisch bringt genau das die eigentliche Schwierigkeit mit sich, denn anders als Bambera steht Liviana öffentlich und ohne Login im Netz: Jeder Mensch und jeder Bot der Welt kann Anfragen schicken, die bei Amazon Bedrock Geld kosten.

Rundgang durch die Anwendung

Der Auslöser

Auf jeder kommerziellen Seite sitzt unten rechts das Maskottchen von KettenKI. Kein fremdes Chat-Symbol, sondern die Figur, die auch auf der Produktseite steht: Der Einstieg in das Gespräch ist Teil der Marke und nicht ein aufgeklebtes Fremdprodukt. In den Portfolio- und Blog-Bereich kommt sie bewusst nicht, dort ist das Publikum ein anderes.

Geöffnetes Fenster

Ein Klick öffnet das Fenster mit einer kurzen Begrüssung. Die Oberfläche übernimmt die Farben und die Schrift der Seite, damit der Chat wie ein Teil des Hauses wirkt. Unter dem Eingabefeld steht dauerhaft der Hinweis, dass es sich um einen Prototyp handelt und Antworten Fehler enthalten können.

Eine echte Anfrage

Eine Yogaschule fragt, ob ein Chatbot ihr die wiederkehrenden Fragen per E-Mail und WhatsApp abnehmen könnte. Die Antwort bleibt kurz, bleibt beim Thema und endet mit dem Weg zum Kontakt. Der Aufruf zum Kontakt kommt nur bei erkennbarem Kaufinteresse und nicht unter jeder Antwort. Geantwortet wird ausserdem in der Sprache der Frage, auch auf Spanisch, obwohl die Website selbst nur Deutsch und Englisch kennt.

Ausserhalb des Themas

Jemand versucht, ihr das Passwort zum AWS-Konto zu entlocken. Sie lehnt ab und benennt, worüber sie spricht. Der Themenrahmen steht im System-Prompt und wird nicht als Zufall behandelt: Liviana redet über KettenKI und die drei Lösungen, nie über Javier als Bewerber, nie über Preise, die es öffentlich nicht gibt, und nie über die technischen Innereien der anderen Produkte.

Architektur

Das Widget schickt ausschliesslich die neue Nachricht und eine Sitzungskennung an eine HTTP-API von API Gateway, die das Throttling und die erlaubte Herkunft regelt und danach die Lambda aufruft. In der Lambda läuft die Prüfung in einer bewussten Reihenfolge: erst die Sperre pro Sitzung, dann der Verlauf, dann der Tageszähler und erst danach das Modell. Die billigste Absage kommt zuerst, und der Tageszähler wird unmittelbar vor dem bezahlten Aufruf erhöht, damit eine abgewiesene Anfrage kein Kontingent verbraucht. Den Verlauf und die Zähler führen zwei DynamoDB-Tabellen mit TTL, das Wissen über KettenKI liegt als einzelnes Dokument in S3 und wird im Ausführungskontext fünf Minuten zwischengespeichert. Die eigentliche Antwort kommt von Claude Haiku 4.5 auf Bedrock. Parallel dazu melden CloudWatch-Alarme und ein AWS-Budget per SNS und E-Mail, wenn etwas aus dem Ruder läuft.

Stack

Ebene Technologie
Frontend Widget in Vanilla JS, ohne Build-System
API API Gateway HTTP API, mit Throttling und fester Herkunft
Rechenleistung AWS Lambda (Python 3.13)
Modell Claude Haiku 4.5 über Amazon Bedrock (eu-central-1)
Persistenz Amazon DynamoDB, zwei Tabellen mit TTL
Inhalt Amazon S3, ein JSON-Dokument, im Ausführungskontext zwischengespeichert
Infrastruktur CloudFormation von Hand, ohne SAM und ohne CDK
Monitoring CloudWatch-Alarme, SNS und ein AWS-Budget

Was ich gemacht habe

  • Die Lambda nach dem Ports-und-Adapter-Muster gebaut: Die Fachlogik kennt nur Protokolle, die konkreten Adapter für Bedrock, S3 und DynamoDB hängen aussen dran. Zwei zusätzliche Adapter, ein Ablage im Arbeitsspeicher und ein Modell-Doppel, lassen das ganze System ohne ein einziges AWS-Konto laufen und testen.
  • Den Kostenschutz in fünf Schichten entworfen und umgesetzt, statt eine Web Application Firewall zu mieten (siehe Technische Herausforderung).
  • Zwei DynamoDB-Tabellen statt einer angelegt, eine für den Gesprächsverlauf und eine für die Zähler. Sie haben unterschiedliche Schlüssel, unterschiedliche Lebensdauern und unterschiedliche Schreibmuster; sie zusammenzulegen hätte nur eine Zeile Infrastruktur gespart und dafür jede Abfrage verkompliziert.
  • Beide Zähler mit einer bedingten Aktualisierung durchgesetzt. Ein Lesen mit anschliessendem Schreiben hätte zwei gleichzeitige Anfragen beide am Limit vorbeigelassen; so ist es ein einziger Rundlauf, atomar, und eine abgewiesene Anfrage schreibt gar nichts.
  • Das Wissen über KettenKI aus dem Code herausgezogen und als einzelnes Dokument nach S3 gelegt. Was Liviana weiss und wie sie auftritt, ändert sich damit durch das Hochladen einer Datei und nicht durch ein Deployment.
  • Das Widget in dieser Website gebaut: Zustände für Tippen, Sperre, erschöpftes Tagesbudget und Netzwerkausfall, Sitzungskennung im Browser, Sprachwechsel über dasselbe System wie der Rest der Seite.

Technische Herausforderung

Ein Sprachmodell öffentlich und ohne Login ins Netz zu stellen, heisst, einen Knopf anzubieten, der bei jedem Druck Geld kostet und den man selbst bezahlt. Die naheliegende Antwort wäre eine Web Application Firewall gewesen, aber die kostet ab der ersten Minute eine feste Monatsgebühr, unabhängig davon, ob überhaupt jemand vorbeikommt. Für eine Demo steht das in keinem Verhältnis. Stattdessen habe ich fünf Schichten übereinandergelegt, die alle nichts kosten: eine reservierte Nebenläufigkeit als harte Obergrenze gleichzeitiger Aufrufe, das Throttling des API Gateway, eine Sperre von zwanzig Nachrichten je Minute und Sitzung, einen Tageszähler von fünfhundert Aufrufen als Sicherung und ein Limit für die Länge von Frage und Antwort. Interessant an dieser Aufgabe war weniger die Technik selbst als die Reihenfolge: Jede Prüfung sitzt dort, wo sie am wenigsten kostet, und der Tageszähler wird erst unmittelbar vor dem bezahlten Aufruf erhöht. Eine abgewiesene Anfrage verbraucht damit nichts, ein fehlgeschlagener Aufruf bei Bedrock dagegen schon, denn versucht wurde er.

Ergebnis & Learnings

Liviana läuft seit August 2026 auf kettenki.com, antwortet in drei bis fünf Sekunden und in der Sprache der Besucherin. Sie ist gleichzeitig das Produkt und der Beweis, dass es funktioniert. Mitgenommen habe ich vor allem eines: Bei einer öffentlichen Funktion mit einem Sprachmodell steckt die eigentliche Ingenieurarbeit nicht im Prompt, sondern in der Frage, was passiert, wenn es schiefgeht. Was, wenn jemand sie flutet, wenn Bedrock ausfällt, wenn das Tagesbudget aufgebraucht ist, wenn jemand versucht, sie aus ihrer Rolle zu holen. Auf jede dieser Fragen gibt es hier eine Antwort im Code und einen verständlichen Satz für die Besucherin.
